## Findings

### Critical - Supabase Policies Are Still Demo-Wide

The current sync policy file uses temporary demo policies such as:

- `using (true)`
- `with check (true)`

Impact:

- Browser UI permissions are not enough for production security.
- A user with the public anon key can potentially read/write tables directly if these policies are active.
- Participant-only and teacher-only restrictions can be bypassed outside the UI.

Recommendation:

- Replace demo-wide policies with role-aware Supabase RLS policies.
- Move privileged writes to a backend/API layer or Supabase Edge Function using service-role logic.
- Keep public access limited to upcoming program listing and guest registration only.

### Critical - Business Data Is Rendered With `innerHTML`

Many screens render user-entered values through template strings and `innerHTML`.

Impact:

- A malicious value entered into fields such as name, notes, address, course name, teacher name, or eligibility could render HTML in the app.
- This creates stored XSS risk if unsafe text is saved in Supabase and later viewed by another user.

Recommendation:

- Add HTML escaping for all user-entered values before rendering in template strings.
- Prefer DOM creation/textContent for future UI rendering.
- Test with values such as `<script>alert(1)</script>` and `<img src=x onerror=alert(1)>`.

### High - Login Depends On Full Data Load

The login function currently blocks if `hasLoadedRemoteData` is false.

Impact:

- If one data table is temporarily unavailable, login cannot proceed even if Supabase Auth is working.
- This can make troubleshooting harder for admins.

Recommendation:

- Consider allowing login first, then loading role-scoped data after authentication.
- Show module-level loading/failure states instead of blocking the entire app.

### High - Supabase Anon Key Is Public, So RLS Must Be Production-Grade

The anon key in `supabase-config.js` is expected for a browser app, but it means database security must be enforced in Supabase, not only in JavaScript.

Impact:

- This is acceptable only if RLS policies are strict.
- With demo-wide policies, this is not production safe.

Recommendation:

- Do not deploy with `temporary_demo_*` policies.
- Add a production RLS script and keep the demo script clearly separated.

### Medium - Browser-Control Output Is Currently Not Returning Readable Snapshots

The in-app browser controller connects, but text snapshots are not being returned to the chat in this session.

Impact:

- Automated visual verification from this chat is limited.
- Manual confirmation in the open browser is still needed for login/password workflows.

Recommendation:

- Continue source-level audit and manual UAT together.
- User should enter credentials directly in the browser; do not share passwords in chat.

## Blocked / Needs User Action

- Supabase Table Editor verification: requires access to the Supabase console or user confirmation after each save/edit/delete.
- End-to-end data creation tests: should be done only after confirming this is a test/staging Supabase project or using disposable test records.
